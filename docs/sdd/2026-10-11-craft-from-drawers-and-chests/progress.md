## Rulings

Ruling 1: **`Logic` indexes storage by prefab name, not `m_shared.m_name`.** Item Drawers' ZDO `"Prefab"` holds a prefab name, and both MultiUserChest and AzuCraftyBoxes key by prefab; CraftFromContainers' `CountItems(m_shared.m_name)` therefore cannot be ported verbatim. `PullRequest.ItemName`, `StorageStock.ItemName` and `IStorageSource.Count(itemName)` all carry a prefab name, and the chest source counts by `item.m_dropPrefab.name`. Carried into T4, T10, T11, T13. — *Cost if wrong:* chest and drawer counts disagree with the requirement and nothing ever pulls; the first in-game craft check catches it.

Ruling 2: **The drawer-contract resolution becomes pure logic.** `Logic/DrawerContract.cs` resolves which Item Drawers contract is available through an injected `Func<string, Type>`; `Storage/DrawerApi.cs` is a thin game-facing wrapper over it. This is what lets T9's soft-dependency test run in the Tests project without Unity. Carried into T9. — *Cost if wrong:* T9's test is dropped and the fallback is verified only by hand in game.

Ruling 3: **The off-switch key moves earlier than T12.** The ZDO key constant lives in `Logic/ConfigModel.cs` (T5) and each source reads it through `StorageToggle.IsOff`-equivalent logic introduced with the sources in T9/T10; `Toggle/StorageToggle.cs` (T12) owns only `Flip`, the hotkey and the hover text. Carried into T9, T10, T12. — *Cost if wrong:* T12 has to re-plumb the interface.

Ruling 4: **Test steps that list test names with their expectations are sufficient** rather than full bodies, provided every dispatch tells the implementer to write a concrete assertion per name — no test may assert nothing. — *Cost if wrong:* thin tests; the task reviewer flags them Important and the fix loop adds the assertions.

Ruling 5: **T10 constructs `ChestTypeRules` from `FeatureFlags` itself.** T10's Interfaces block omits both types; the dispatch carries the field names from T5 and the rule fields from T2. — *Cost if wrong:* T10 cannot build the eligibility predicate and the task blocks.

Ruling 6: **Staging `MultiUserChest.dll` into the reference layout is owned by Task 6.** The plan's Files and Steps never covered it, but T1's csproj references `$(ReferencesRoot)\Mods\MultiUserChest.dll` and nothing generates that file. T6 gains a step: give `tools/New-ValheimRefs.ps1` a `-MultiUserChestDll` parameter (defaulting to the installed mod set's copy) that writes `<OutputPath>\Mods\MultiUserChest.dll`. Until then the product project deliberately does not compile. Carry into T6. — *Cost if wrong:* the product never compiles for want of a reference; caught the first time `Build.ps1` runs after T1.

Ruling 7: **The skill's per-role model selection was not applied.** This harness exposes no list of dispatchable models, and an unrecognised model name fails the dispatch outright, so implementers and reviewers were dispatched without an explicit model. — *Cost if wrong:* every subagent inherits the session's model, so the run costs more than the skill intends; it does not affect correctness.

Ruling 8: **Toolchain ideas from `ghstwhl/XPortalNetworksTribesPins` fold into Task 6, and the `Docs/` T4 pipeline is not adopted.** Borrow the build mechanics — `Directory.Build.props` with a conditional `ReferencesRoot` and `ValheimGameVersion` as the single source of truth, a `DoPrebuild.props`, `REFERENCES.md`, `Microsoft.NETFramework.ReferenceAssemblies` in `packages.config`, and the csproj's explicit Unity module references plus `MSBuildWarningsAsMessages`/`NoWarn` hygiene. Do not adopt the `Docs/` T4 documentation pipeline: `Build.ps1` treats the generated manifest as optional, this mod's README/CHANGELOG/icon are hand-written in Task 6, and the no-Nexus constraint removes the pipeline's other output. Task 6 may therefore amend `Directory.Build.props` and the csproj conventions Task 1 established. — *Cost if wrong:* Task 6 grows by the docs pipeline and its templates, and the hand-written README steps are dropped.
